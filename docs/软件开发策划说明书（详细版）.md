## 1. 项目摘要与建设目标

团播联动台是一套 Windows 原生 Electron 演出联动桌面软件。核心目标是让操作员围绕歌曲完成节目管理、画面编排和灯光编排，再用真实音乐位置或 P1 时间码可靠驱动现场动作。

系统已有节目、媒体、播放、OBS、P1、灯光和 MA2 同步的实现基础。下一阶段重点是补齐现场验证、跨设备适配和故障恢复闭环，形成可交付、可复现、可维护的稳定版本。

### 1.1 产品价值

- 操作集中：歌曲、时间点、画面切换与灯光引用在同一工程中管理。
- 保留现场资产：复用用户的 OBS 完整场景及滤镜，复用 MA2 已编好的灯光 Cue。
- 支持两种主控：内部音乐主控与 P1 跟随显式选择，适应不同现场。
- 可解释失败：知道哪个目标、哪个动作、哪个阶段失败，避免“显示成功但外部未执行”。
- 可恢复编排：工程自动保存、撤销/重做、同步备份与回读降低编辑和联调损失。

### 1.2 阶段成功标准

| 目标 | 验收方式 |
| --- | --- |
| 编排可重复 | 保存重开后歌曲、素材入点、Cue、灯光、模板与绑定一致 |
| 时钟可信 | 用真实媒体位置或真实 MTC 驱动，断源后不继续空跑 |
| 原 OBS 视觉保持 | 完整场景模式前后对比来源、变换、滤镜，除授权自有音频项外不产生意外修改 |
| 灯光同步可信 | 写前备份、版本复核、冲突处理、写后回读均有证据 |
| 现场可操作 | 操作员独立完成连接、预检、播放、中断处理和停止清理 |
| 可安装交付 | 固定版本产物通过 Windows 安装、覆盖、启动、更新及卸载验收 |

不设未经测量的“所有设备兼容”“零延迟”“绝不丢码”“完全无损”等指标。

## 2. 用户、角色与核心场景

### 2.1 角色

| 角色 | 主要任务 | 关键诉求 |
| --- | --- | --- |
| 现场播放操作员 | 选歌、启停、排练、观察状态、处理失败 | 操作集中、状态明确、停止可靠 |
| 视频/导播人员 | OBS 场景、采集设备、滤镜和正式输出 | 原视觉设置不被联动覆盖 |
| 灯光编排人员 | 时间点、Cue 引用、Executor 与 Master | 快速打点、复用编排、可靠同步 |
| 系统集成人员 | MIDI、网络、插件、账号、版本和音频路由 | 分层检测、定位失败、清晰兼容范围 |
| 开发与测试人员 | 维护代码、回归、构建和现场验收 | 可追踪需求、确定性测试、可复现证据 |

角色划分用于工作责任，不表示本版已实现多用户权限系统或在线协作。

### 2.2 核心使用场景

**场景 A：内部主控演出。** 导入音乐，选择 OBS 输出模式，编排画面和灯光，预检后从歌曲卡片播放。音乐实际位置驱动 OBS、MIDI 和 MTC。暂停、定位和停止均有明确外部清理。

**场景 B：沿用 P1。** 读取 P1 音频工程并生成独立联动工程，操作员在 P1 开歌。联动台根据已映射时间码自动匹配节目，执行当前歌曲编排。

**场景 C：保留 OBS 拉腿场景。** 用户在 OBS 完成视觉调校，联动台只安排完整场景切换；内部音频按明确规则跨场景继续输出。

**场景 D：独立灯光编辑。** 不启动 REAPER，在歌曲波形旁打 Cue、编辑事件和 Master；默认试听不输出，显式联动才发送设备。

**场景 E：控台往返。** 读取 MA2 Timecode 到当前节目，修改后读取控台最新状态，解决三方冲突，备份、写入、回读，并刷新共同基线。

**场景 F：现场故障。** OBS 断线、MTC 丢失、MIDI 拔出或同步超时后，显示具体失败，不切换主控、不自动重发不确定命令；由操作员核对状态并恢复。

## 3. 产品范围及外部边界

### 3.1 范围内

节目单、资源与参考波形、内部正式音乐、P1 跟随、画面和灯光时间线、OBS WebSocket 动作、受管媒体、完整场景切换、MIDI/MTC、限定 MA2 Timecode 同步、外部程序生命周期、预检、后台日志、安装与更新。

### 3.2 明确排除

- Program 窗口、Electron 内置视频合成、libobs helper。
- 联动台直接摄像头/麦克风采集、RTMP、NDI、虚拟摄像头。
- 控制 OBS 开始/停止推流或录像，以及直播伴侣开播/关播。
- 编辑 MA2 Cue 内部灯具参数、替代 MA2 灯光引擎、完整 Show 克隆。
- 旧 ShowPackage 迁移，以及未经用户要求重新提供 IBC 工程导入。
- 未经确认的云同步、多人协作、订阅收费、加密狗和反调试系统。

### 3.3 外部系统规则

OBS 正式画面由 OBS 完成；只有应用拥有的受管对象可按规则更新/移除。完整场景模式允许目标场景增加应用自有内部音频项，但不得改用户视觉来源、裁剪或滤镜。

外部程序按精确路径、PID、启动时间和所有权识别。只正常关闭本次由联动台启动的进程；拒绝关闭时保留，不强杀。

直播伴侣的产品边界至多为进程与主窗口检测；现有运行链路不以其状态作为 OBS/P1 联动前置，不将启动、关闭或开播管理列入研发范围。

## 5. 功能需求设计

优先级定义：P0 为稳定交付门槛，P1 为显著改善效率和兼容性，P2 为可另行评审的增强。优先级不自动授权扩大产品范围。

### 5.1 工程与节目管理（PRJ / P0）

**输入：** 工程文件、音乐和本地媒体、节目参数。  
**处理：** 严格 schema 校验，Command 提交，原子保存，资源复制与校验，历史记录管理。  
**输出：** 可重开的工程及资源目录、保存状态和明确错误。

要求：

1. 区分工程数据、机器配置和缓存，机器变化不污染可移交工程。
2. 异步导入/保存必须绑定原工程身份，切换工程后旧结果不得写入新工程。
3. 保存失败保留原文件；不能自动生成空工程覆盖。
4. 名称、备注等未发生变化时不提交空操作；错误输入恢复或保留可解释状态。
5. 轨道、片段、素材和同步对象使用稳定 ID，撤销重做不改变后续引用。

验收：编辑—撤销—重做—保存—关闭—重开一致；跨工程异步操作、文件损坏、无权限和磁盘故障有针对性用例。

### 5.2 音乐与节目播放（PLY / P0）

保持内部主控与 P1 跟随显式选择。覆盖裁剪、音量、淡入淡出、暂停/继续、定位、重播、上下首和逐曲结束行为。有效播放时钟始终来自选定主控。

切歌应完成旧会话清理、目标预检和媒体准备，不能为了表面连贯跳过检查。无缝连播不是现有承诺；若后续提出，需单独设计音频预加载和交接状态并确认范围。

验收：开头/尾部事件只按规则执行；暂停定位保持暂停；停滞、断线、结束和切歌释放活动输出；音频与界面时钟分离后仍一致。

### 5.3 媒体、画面与 Cue（VIS / P0）

完整场景模式维持用户既有 OBS 视觉；受管模式发布自有媒体和引用。预检校验目标、动作兼容性、资源身份、画布与所有权。

素材编辑保留入点，拆分/左修剪后不得从原始零点误播。停止追踪已成功或可能执行的对象，清理失败保持可见状态。

来源创建流程保留草稿、参数回读和取消清理。针对八类来源分别验证实际信号，不能用一个模拟设备通过推断所有类别完成。

验收：用户 OBS 场景集合前后对照；完整场景定位恢复；媒体入点/结束与原声；编辑器预览不意外切 Program 或启动声音。

### 5.4 MIDI 与 MTC（MID / P0）

区分 MTC 输入、MTC 输出、控制输入、事件输出和反馈输入；配置错误需要明确阻断或报告。检查真实消息、顺序、端口生命周期及通道/设备号，不只看枚举状态。

原始 MIDI 事件保留其原始地址；MSC 设备号只影响应由当前设置生成的指令。MA2 Goto、下一步 Go、Off 和通用 MSC Stop 不混为一谈，各输出通路按能力编译，不能错误替换。

验收：字节级编码、长音符收尾、Note Off 力度、SysEx 完整性、定位不补发历史动作、物理端口延迟与丢失测量。

### 5.5 灯光时间线（LGT / P0、P1）

保持当前音乐旁直接打点工作流。轨道支持静音/独奏/锁定/排序；事件支持单选/多选、复制、批量调整和跨节目复用；曲线支持可解释的边界处理。

时间锁定和节拍锁定分别保持语义。BPM 渐变要在编辑显示、编译调度、文件交换中使用相同时间换算。区域循环必须验证末尾事件、短音符和重新进入循环的状态。

录制接收真实反馈时保持消息身份；缺少绑定不得猜 Cue 或 Sequence。并发编辑、轨道锁定、端口断开、定位回跳均需完成录制收尾。

验收：真实播放打点与波形位置核对、十万事件界面操作、音符释放、模板与剪贴板往返、录制原始字节和转换结果可追踪。

### 5.6 文件交换（EXG / P1）

支持范围以已验证格式为准。每次导入提供预览、警告与确认，损坏结构或歧义不可静默跳过。

RPP 重点维护原生 6.05 样例和独立预期结果，覆盖实际 Take、变速、偏移、倍速、循环、轨道状态和 SysEx。Take FX、其他插件或未知格式必须在转换报告暴露。

MIDI 扩展需版本化；标准事件被外部软件修改后，不能用旧扩展覆盖用户的新改动。文件时间网格、整数 BPM 编码、曲线采样属于精度边界，报告应说明。

验收：原生来源—转换预览—导入—保存—导出—重新导入，分别比较标准数据与本软件扩展；不以自身往返替代第三方兼容验收。

### 5.7 MA2 连接与同步（MA2 / P0）

维持本机文件桥和网络连接两条适配路径，共用类型化数据、对象限制和事务服务。网络目标切换使旧会话及预览失效；播放期间禁止更换目标或写工程。

网络发现只做只读特征识别，限制并发、网段和超时，支持取消与手动地址。最多 128 个保存目标不等于同时控制 128 台。

后续必须在允许登录的账号下验证真实双通道认证、插件调用、大响应分块、完整同步、权限拒绝和中断恢复。实体控台版本能力与 XML 表现逐台记录。

验收：参见第 9、12 节。任何未知写入结果不显示“同步成功”。

### 5.8 预检、故障与维护（OPS / P0）

按当前主控模式检查必要设备；内部主控不能要求 P1，未使用灯光不应强制要求灯光设备。稳定 MTC、素材、OBS 库存、音频路由、画布等检查结果明确区分通过、警告和阻断。

后台日志保留动作目标、阶段、错误和恢复线索，并移除凭据。当前界面已取消独立日志/诊断入口，后续若需恢复导出入口，应先确认位置和必要性，不重新堆叠设置页。

## 6. 数据、文件与兼容设计

### 6.1 数据分区

| 分区 | 内容 | 约束 |
| --- | --- | --- |
| 工程 | 节目、Cue、素材相对路径、灯光、模板、绑定基线 | 可移交；不得保存设备密码、MIDI 端口名、外部 exe 绝对路径 |
| 本机档案 | OBS、MIDI、MA2 目标、外部程序设置 | 与当前电脑关联；网络凭据按目标隔离 |
| 安全存储 | OBS/MA2 密码和更新凭据 | `safeStorage`；不可用时失败，不回退明文 |
| 缓存 | 波形、缩略图、编辑代理 | 可重建；不能替代正式源文件 |
| 运行证据 | 脱敏日志、测试结果、同步备份索引 | 不泄露账号密码；与工程保存成功区分 |

### 6.2 版本策略

普通工程继续 v1，灯光工程采用 v2。字段增加必须明确旧版行为；旧软件应拒绝覆盖不支持的数据。不能以宽松解析悄悄丢弃新字段。

交换扩展、MA2 桥协议和机器档案各自维护明确版本。迁移采用显式校验和错误，不增加补丁式兼容分支掩盖未知结构。

### 6.3 一致性要求

资源使用相对路径和摘要；同步对象使用业务身份及基线，不能把 XML index/path 当成永久 ID。回读比较保留未知扩展及子节点顺序等重要内容，避免只比较已知字段导致丢失被漏报。

## 7. 系统架构与接口设计

完整链路图与接线表见[系统原理与拓扑说明](系统原理与拓扑说明.md)。

### 7.1 分层

```text
Schema / Domain
    ↓
Registry / Adapters
    ↓
Stores / Runtime
    ↓
Components
    ↓
最小 IPC 边界
```

以上为项目规定的分层方向。具体主进程提供文件、OBS、进程和网络等边界能力；渲染侧通过类型化桥使用，不把业务判断塞进 IPC。

| 位置 | 责任 |
| --- | --- |
| `packages/schema` | Zod 工程、灯光、设备、MA2 和 IPC 契约 |
| `packages/core` | Command、时间码、Cue 状态机、编译、导入、预检及同步领域逻辑 |
| `apps/desktop/src/main/link` | 工程文件、OBS、网络、进程、安全存储、日志和更新适配器 |
| `apps/desktop/src/preload` | `tbLink` / `tbFile` 类型化桥 |
| `apps/desktop/src/renderer/src/registry` | MIDI 等设备适配 |
| `apps/desktop/src/renderer/src/link` | 状态仓库、播放协调、时间线和界面 |
| `tools/ma2`、`tools/obs` | 配套插件、脚本与说明 |

### 7.2 修改规则

所有工程修改封装为 `LinkCommand`，经文档 store 的 execute 系列入口提交。组件不能直接改工程；异步回读同样要验证工程身份后通过 Command 应用。

TypeScript 严格模式、穷举联合类型、边界 Zod 校验。禁止 `any`、`as any`、空 catch、`eslint-disable` 以及未解释的静默 fallback。

### 7.3 外部接口

| 接口 | 规则 |
| --- | --- |
| OBS WebSocket | 请求默认 2 秒超时；明确目标与所有权；不自动重试业务动作 |
| MIDI | 发送与接收订阅独立；只报告实际可知的传输状态 |
| MA2 本机桥 | 序列化请求、固定协议、限定目标、默认已有 15 秒超时策略、不重放旧请求 |
| MA2 网络 | 命令/监视双通道、关联标识、完整分块、目标身份验证 |
| 文件 | 校验大小/格式/身份，原子写入，防止旧预览修改新文件 |
| 进程 | 精确身份和所有权；正常关闭，不强杀 |

超时值按适配器明确定义，不能把 OBS 默认 2 秒套用全部 MA2 事务。

## 8. 时钟、调度与运行状态

### 8.1 时钟源

内部主控采用媒体实际播放位置；P1 跟随采用解码后的真实 MTC。单次运行会话只能有一个明确时钟源，不因断线自动切换。

参考舞台、波形滚动和界面动画允许平滑显示，但不能成为正式 Cue 的独立时间源。调度与 React 渲染分离，取消未来排队动作时必须真正影响输出队列。

### 8.2 状态设计

以下是验收用的概念状态，不要求替换现有源码状态名：未准备、预检、待命、运行、暂停/冻结、停止清理、错误。

| 触发 | 应有行为 |
| --- | --- |
| 预检阻断 | 不进入正式运行 |
| P1 等待开头 | 保持待命，收到符合规则的真实时间码才开始 |
| 稳定连续跨过 Cue | 按顺序执行当前节目的到期动作 |
| 丢码/异常跳变 | 冻结自动 Cue，不猜测遗漏动作 |
| 暂停/定位 | 取消旧队列、释放活动音符、按模式恢复画面状态 |
| 停止 | 清理成功或可能执行的应用拥有对象；失败仍保留错误 |
| 直播单动作失败 | 标记失败并继续后续，不自动重试 |
| 排练单动作失败 | 阻断后续动作 |

### 8.3 测量计划

已有 30 fps 一小时本机回环证据可作为回归基线，不能代替硬件验收。新增测量分别记录媒体位置、发送时间、接收时间和控台观察结果，避免混合软件相位与灯具响应延迟。

建议软件回环先沿用现有一帧以内相位/漂移门槛；实体 MIDI 和控台端到端阈值应在目标设备实测后签定。后台、最小化、波形首次生成、切歌、十万事件和端口拔插都应纳入场景。

## 9. MA2 同步事务设计

### 9.1 范围

只同步绑定的 Timecode、轨道、事件、Cue 引用、执行器动作和已支持 Master 点；不写 Cue 内部灯具参数。创建对象必须明确目标编号，不覆盖用户已有未知对象。

### 9.2 三方比较

共同基线代表上次双方确认的状态；本地是当前节目；远端是本次最新回读。单方修改可形成候选合并，双方修改同一对象或修改与删除相撞时进入冲突。

重复 Cue 或原生索引变化导致身份不明时，先确认对应关系，再进行冲突合并。错误的身份匹配不能靠“以本地为准”自动覆盖。

### 9.3 写入流程

1. 验证连接、插件能力、绑定范围及当前未播放。
2. 固定当前工程和目标身份，获取通信互斥。
3. 复核预览版本、Timecode 和引用序列是否变化。
4. 显示合并结果和时间/值量化调整。
5. 保存可定位的写前备份。
6. 编译并写入限定目标。
7. 回读完整目标，对比事件、引用、轨道、Master 和未知保留内容。
8. 确认后通过 Command 更新本地与基线。
9. 释放锁并显示最终状态。

### 9.4 失败处理

写前失败标明未写；写中超时标明可能已写；控台已确认但本地保存失败标明双方基线未完成更新。所有情况保留备份定位信息，不自动重试、不自动回滚。

软件内播放锁不能完全阻止操作员在实体控台修改，因此仍需远端版本复核与回读。若适配器无法可靠检查预期版本，不应启用生产写入。

## 10. 界面与交互原则

保持现有“节目单、编辑器、设置”结构。设置仅保留设备连接、播放、画面与同步、外观与更新；灯光编辑工具随时间线上下文打开，不新建重复管理页。

所有属性保持统一字号、底色、间距和字段逻辑。先选对象再编辑；轨道、单 Cue、多选 Cue 各自展示对应属性，避免混入控台连接字段。

播放、停止、连接状态和错误提示应清晰可见；长名称不能撑破窗口。键盘焦点、输入状态、模态窗口和快捷键相互隔离。图标采用 lucide-react，不用 Emoji。

后续正式 UI 任务按项目要求加载 frontend-design；TypeScript 实现按项目要求加载对应 TypeScript skill。技能不可用时明确说明并遵循现有设计/工程规范，不假称已加载。本次仅编写说明文件，未修改 UI 或 TypeScript。

## 13. 分阶段研发计划

### 阶段一：冻结现状与验收清单（P0）

盘点最新代码和历史记录冲突，确定两种主控、两种 OBS 模式和 MA2 适配范围。建立需求—实现—证据矩阵，记录当前源码快照及未提交状态。

交付物：现状说明、详细策划、兼容矩阵初稿、未完成事项和测试工程清单。退出条件：没有把旧缺口当成当前缺口，也没有把模拟结果当实机结果。

### 阶段二：MA2 网络与实体控台闭环（P0）

使用真实授权账号完成双端口登录和插件调用；在专属对象验证读取、创建、轨道/Cue/Master 写回、冲突、超时与回读。逐版本检查时间单位、值量化、尾长和对象重排。

交付物：网络实机报告、目标版本兼容矩阵、修复及回归、插件安装说明。退出条件：限定版本上完整同步闭环通过；无法支持的能力明确禁用并记录。

### 阶段三：OBS 与音频现场闭环（P0）

验证用户真实完整场景拉腿/滤镜、转场、应用音频跨场景连续、受管媒体入点和停止清理；逐类确认采集来源及编辑预览。分别验收内部主控与 P1。

交付物：OBS 场景对比、正式音频路由记录、关键故障录像/日志。退出条件：正式画音与编辑预览职责一致，用户场景无意外修改。

### 阶段四：灯光编辑、交换与性能收敛（P0/P1）

完成真实 MIDI 反馈录制、循环边界和调度互斥；补齐未覆盖原生文件，完善转换报告；测量十万事件 GUI 及物理 MIDI 长场次。

交付物：原生样例、转换兼容表、性能/时序报告、关键工作流回归。退出条件：编辑、文件交换和实际输出结果一致，不能支持的范围明示。

### 阶段五：候选冻结与 Windows 交付（P0）

冻结需求和版本，执行全量验证、发布产物检查、独立账户安装与更新、十首节目演练，复核文档与实际入口。

交付物：安装包、发布清单与 SHA-256、插件、说明书、验收报告和已知问题。退出条件：代码、产物和证据对应同一候选快照，经授权后才提交、推送和发布。

### 阶段六：稳定维护（P1/P2）

围绕现场问题进行小版本修复；根据真实需求评审混音参数、其他格式或设备支持。独立 MTC 测试面板、默认 MIDI 参数面板等属于可评审增强，不应因 IBC 中存在就直接插入当前开发范围。

## 15. 风险与应对

| 风险 | 影响 | 应对 |

<a id="当前链路"></a>
## 当前链路

2026-10-23 起的客户端行为（尚未随正式版发布；已发布的 0.4.29 仍是旧行为）：

- 更新源：`https://updates.tuanbo-link.jinhefilm.com/windows/x64/`，`electron-updater 6.8.9` 的 generic provider。唯一配置来源是 `apps/desktop/package.json` 的 `build.publish.url`；主进程直接引用它，打包生成的 `app-update.yml` 由 `verify-desktop-artifacts.mjs --dist` 核对一致。
- 客户不填写 GitHub Token，不需要公司网站账号；旧更新 Token 的 IPC、schema 和输入 UI 已移除。已有本地加密凭证不会被静默删除，也不会迁移到公司服务。
- 检查：安装版启动约 10 秒后在后台检查一次，只写日志并在工作区提示一次新版本，不下载。后台检查失败（现场断网常见）记为警告，面板显示「启动时未能检查更新…可以在软件更新中重试」，不显示为更新错误。手动检查在「设置 › 外观与更新 › 软件更新」。检查和读取更新状态不需要授权：未激活、授权到期或启动联网校验失败的电脑在激活页也能看到新版本。
- 发布签名：发现新版本后先用内置公钥验证 `latest.yml` 里的发布签名（见[发布签名](#发布签名)），并核对签名内容与 `latest.yml` 的版本、安装包名、大小、sha512 一致。签名缺失或不符时显示新版本和原因、写运行日志，不提供下载和安装。下载完成后和安装前各重新计算一次安装包的 sha512 与签名比对，不符即拒绝安装。
- 升级服务期限：用签名里的发布日期和本机签名授权里的 `updatesUntil` 比较。发布日期晚于期限或授权不可用时，面板显示新版本和原因，不提供下载和安装；下载前、安装前各再核对一次授权。日期按北京时间显示，比较用精确时刻。
- 下载：手动点击，差分下载（2026-10-23 起）。安装器每次安装都会把自己复制到 `%LOCALAPPDATA%\@tbdesktop-updater\installer.exe`，更新时按新旧版本的 blockmap 只下载变化的块，再用本机缓存拼出完整安装包；拼出的文件 SHA-512 与 `latest.yml` 不符时自动改为下载完整安装包。最终文件仍要通过 SHA-512 和发布签名校验才会安装。下载和安装仍需要有效授权。播放中不能开始下载；下载中开始播放会立即停止下载并回到「可下载」，停止播放后可以重新下载。检查与下载互斥，已下载的版本保留等待安装。
- 安装：播放中拒绝。确认后走与关闭软件相同的退出流程：未保存工程「保存 / 不保存 / 取消」→ 停止灯光试听 → 关闭正式音频与画面 → 逐项确认由本软件启动的外部程序 → 关闭音乐分析 → 启动安装程序。任一步选择返回即取消安装，已下载的更新保留。安装程序启动失败时软件保持打开，面板显示错误。安装沿用原目录和当前用户范围，更新后自动重启。
- 开发模式不执行更新。
- 网络层采用锁定版本 `builder-util-runtime` 的 60 秒 socket 空闲超时。完整包传输可超过 60 秒，不是整次下载的总时限；慢链路需实测。授权请求另有独立的 10 秒时限。

当前 feed 是公开静态资源，下载本身不发授权，安装包未做代码签名。升级服务期限由客户端按签名授权执行，属于产品策略，不是防破解措施：任何人都能从官网直接下载安装包。服务器短效下载链接和版本资格目录仍属后续工作。

### 构建身份

每个构建记录产品名、版本、渠道（正式 / 开发）、Git 提交号（有未提交改动时带 `-dirty`）和 appId。正式构建取不到提交号会直接失败。这些信息显示在「软件更新」面板，写入每次启动的日志、导出日志的开头和诊断包。打包版只从 app.asar 加载界面，忽略 `ELECTRON_RENDERER_URL`；从开发机热更新测试电脑界面的做法只对修复前装好的包有效。

### 只发正式包

2026-10-24 起只有正式安装包这一种，测试一律用后台签发的激活码。免激活测试包（`portable-test`，任何机器永久免激活）和内测包（`internal`，构建时嵌入内测许可）连同它们的构建、校验脚本都已删除。

- 打包只接受 `electron-vite build --mode release` 的产物：electron-builder 的 `beforePack` 钩子（`apps/desktop/scripts/require-release-build.mjs`）检查待打包的 `out/main/index.cjs`，含有开发期本机测试入口（`TBLINK_LOCAL_TEST_ACCESS`、`.local-test-access`、「本机开发测试通道」）就拒绝打包。`pnpm dist` 和 `pnpm dist:dir` 会先做 release 构建；先跑 `pnpm build`（开发构建）再直接调用 electron-builder 会被拒绝。
- 正式包的 `--dist` 校验再检查一次 app.asar 不含这些入口，包名和 productName 为正式值。
- 没打包的开发和 e2e 运行保留本机测试入口（`TBLINK_LOCAL_TEST_ACCESS=1` 或 `.local-test-access`）。打包版即使设了环境变量、放了标记文件，也必须激活：`node scripts/verify-packaged-activation.mjs <win-unpacked\团播联动台.exe> <输出目录>` 会同时设置这两样，并断言应用停在激活页、授权不是有效状态、设备输出被拒绝。
- 以前装过测试包的电脑：测试包装在 `%LOCALAPPDATA%\Programs\tuanbo-link-functional-test`，数据在 `%APPDATA%\团播联动台功能测试版`。更早的测试包与正式包同用 `@tbdesktop` 目录和 `%APPDATA%\团播联动台`。这些电脑改装正式包并用激活码激活。
- 离线音乐分析的运行时和模型从 0.5.0 起随正式包发布（用户 2026-10-24 决定），afterPack 按指纹核对，见 [音乐分析工具](../tools/music-analysis/README.md)。

## 同服务器静态出口

不需要 HTML 网页，Nginx 静态站点提供以下文件即可：

```text
/srv/tblink-updates/windows/x64/
  latest.yml
  Tuanbo-Link-Console-X.Y.Z-x64.exe
  Tuanbo-Link-Console-X.Y.Z-x64.exe.blockmap
```

`latest.yml` 由 electron-builder 生成，包含版本、安装包相对文件名、大小和 SHA-512；云端构建再追加 `tblinkRelease` 发布签名。不要手改，改动会让签名或 manifest 摘要失效。正式稳定版本用数字 `X.Y.Z`；当前反向代理白名单不服务 prerelease、其他架构或任意文件。

清单 `Cache-Control: no-store`；带版本的安装包不可变、长期缓存。不开目录浏览，未匹配路径 404。服务器、CF 记录和探测命令见 [COMMERCIAL_DEPLOYMENT.md](COMMERCIAL_DEPLOYMENT.md)。

Git、版本标识、构建位置与服务部署关系见 [完整链路核查](RELEASE_CHAIN.md)。

## 差分更新

2026-10-23 实测（开发机，真实 electron-updater 6.8.9 对本地源，源的 Range 响应与线上 nginx 一致）：

| 场景 | 安装包大小 | 实际下载 | 结果 |
| --- | --- | --- | --- |
| 只改一个界面字符串的两个版本 | 412,792,105 字节 | 1,651,980 字节安装包分段（8 段、1 次请求）加两份约 0.43 MB 的 blockmap | 拼出文件 SHA-512 一致，未回退 |
| 两个真实候选包（中间若干代码提交，美颜和音乐分析不变） | 412,791,934 字节 | 5,498,432 字节（下载计划计算，1.33%） | — |
| 本机缓存的旧安装包损坏 | 412,792,105 字节 | 差分结果 SHA-512 不符后改为完整下载，共 414 MB | 最终 SHA-512 一致 |

2026-10-24 起正式包内置离线音乐分析运行时（固定部分 23,916 个文件、约 2.1 GB）。同日实测（构建机，blockmap 下载计划计算）：

| 场景 | 安装包大小 | 实际下载 |
| --- | --- | --- |
| 内置音乐运行时的正式包，只改一处启动日志字符串的两个版本 | 987,642,297 / 987,642,352 字节 | 1,838,001 字节（0.19%，47,105 块里 88 块不同）；音乐运行时和模型没有重新下载 |

更新源实测下载约 470 KB/s：完整安装包（约 988 MB，0.4.29 升级到 0.5.0 时就是这一种）约 35 分钟；运行时不变的差分更新约几秒到十几秒。要保持这个效果：

- 美颜和音乐分析产物不变时，它们在安装包里的字节不变。这由 electron-builder 的差分友好打包保证（非固实 7z、1 MB 字典，按内容切块的 blockmap），加上仓库里的发布指纹固定产物本身。不要改 NSIS 压缩方式或 `differentialPackage`；升级 electron-builder 后第一次更新可能接近全量。
- 旧 blockmap 的来源：通过软件内更新装上的电脑，在本机缓存里留着当前版本的 blockmap（electron-updater 6.8），跨几个版本也能差分。手动安装的电脑要按当前版本号去更新源取。更新源只保留上一版的 `.blockmap`，更早版本的电脑取不到，会自动改为下载完整安装包。
- 0.4.29 及更早的客户端关闭了差分下载，升级到 0.5.0 时仍下载完整安装包；从 0.5.0 起的更新走差分。

<a id="发布流程"></a>
## 发布流程

2026-10-23 起（替代此前的手工流程和「签名后才能公开」的门槛，用户已决定不办代码签名证书）：

<a id="版本号"></a>
### 版本号

- 正式版本号只在发布提交里改：根目录和 `apps/desktop` 两个 `package.json` 同时改，提交信息 `chore(release): X.Y.Z`。平时的功能提交不改版本号。
- 发布构建（`pnpm verify:release` 和 Release Windows 工作流）要求版本高于所有已有 `vX.Y.Z` 标签和线上 `latest.yml`；它自己的标签只能指向本次构建的提交。日常 `pnpm verify` 只检查两处版本一致。

<a id="发布签名"></a>
### 发布签名

- 安装包不做 Authenticode 签名，manifest 如实记录签名状态；Windows 第一次安装可能提示「无法识别的应用」，官网下载页写了处理方法。
- 我们自己的 Ed25519 发布签名写在 `latest.yml` 的 `tblinkRelease` 字段，内容是版本、渠道、发布日期、安装包文件名、大小和 sha512。客户端内置 `release-2026-10-a`（日常）和 `release-2026-10-b`（离线备用）两把公钥，按 kid 选用。客户端在安装前验签，并核对下载文件；服务器发布前也会验签。
- 本地 `pnpm verify:release` 没有私钥时不签名，manifest 写 `releaseSignature: null`，这样的包只用于安装验收，服务器拒绝发布。

<a id="步骤"></a>
### 步骤

1. 推发布提交到 master；CI 通过后在这个提交上打 `vX.Y.Z` 标签并推送。标签就是发布：之后没有人工步骤。
2. Release Windows：verify 和 build 作业在 GitHub 云端 Windows 上检查、打包、签名，把安装包、blockmap、`latest.yml`、`release-manifest.json` 放进这个标签的草稿 GitHub Release（私有仓库的 Actions 产物存储只有 500 MB，所以不用 artifact）。搬运脚本 `scripts/relay-release.mjs` 下载草稿、按构建清单核对，再上传到服务器 staging：工位电脑的计划任务每 10 分钟（以及登录、联网时）跑一次，Mac 上可以手动 `pnpm release:relay`，二选一，重复运行安全（[发版搬运准备](RELEASE_BUILDER_SETUP.md)）。美颜和音乐分析的固定资产各放在一个 `build-assets-*` release 里，见[固定资产](RELEASE_BUILDER_SETUP.md#固定资产)。
3. 服务器自动发布：staging 里出现新的一份包，root 发布脚本就复制、重新校验，通过就上线。条件是签名有效、manifest 和 sha256 一致、版本高于更新源，并且这个版本以前没上过更新源。更新源只留新版和上一版，更早的移进服务器备份。每份上传只自动尝试一次；没能发布的留在后台「软件更新」的待发布列表，原因写在「最近一次自动发布」。需要撤回时用「回滚到上一版」，撤下的版本也移出更新源，之后重跑工作流也不会再把它自动发上去。完整链路和信任边界见[自动发布文档](AUTOMATED_DEPLOYMENT.md#windows-更新发布打-tag-即上线)。
4. 更新源换成这个版本（`latest.yml` 与草稿里的逐字节相同）后，搬运脚本把草稿转为正式 Release 并标为 Latest：上传后同一次运行最多等 10 分钟，没等到就由下一次运行完成。说明在建草稿时取自 `release-notes/X.Y.Z.md`，没有这个文件就只写固定的激活说明。
   - 搬运某一步失败（工位电脑关机、代理或 GitHub 出错、服务器没能自动发布）只记日志，下一次运行接着做；服务器上已经有这个版本或另一份上传正在进行时，不重复上传。
   - build 失败可以在 Actions 里重跑：草稿里同名的文件会被替换。版本已经上线时，build 拒绝重建。
5. 运行 `node scripts/write-website-release.mjs` 更新官网下载信息并提交，见[官网下载信息](#官网下载信息)。官网改成直接跟着更新源变化之后，这一步去掉。

旧的手工发布（`publish-update.py <目录> <manifest sha256> <提交> <版本>`）仍可用，但同样要求发布签名和更高的版本号。

## 旧安装迁移与故障

已安装的旧客户端仍指向历史 GitHub 源，修改本仓库不会远程改变它们。已核对 `desktop-0.4.27-20260925` 的源码：它要求用户提供 GitHub Token，并访问 `JinHe9527/tuanbo-yijianchufa`；0.4.29 改用公司 HTTPS 源。因此首次迁移使用官网的正式 0.4.29 安装包覆盖安装，不要求客户提供 GitHub Token。当前安装包没有 Authenticode 签名，按文首发布授权如实交付，不得称为签名版本。若以后选择通过旧 feed 发桥接版本，须另行确认旧仓库发布权限与验收，不在本轮执行。旧 0.2.0/0.2.1 的历史下载缺陷仍需要手动跨过。

首次迁移操作：保存并备份 `.tblink` 工程及其引用素材，停止联动并正常退出软件；从官网下载安装器，以原 Windows 用户运行并保留原安装目录。安装后启动 0.4.29，按付费方案输入本机激活码完成联网验证。已有工程不能代替付费授权；不要删除本机配置或把另一台电脑的加密凭证复制过来。原目录覆盖迁移与软件内“重启安装”是两种不同路径，各自验收结果见 [授权与更新验收](LICENSE_UPDATE_ACCEPTANCE.md)。

- “尚未发布可用的正式版本”：检查 `latest.yml` 是否已按白名单路径上线，不能用 HTML 占位页返回 200。
- TLS 失败：核查多级子域名证书、DNS、CAA、云防火墙以及灰云/橙云方式。
- 摘要不匹配：停止交付，检查文件被覆盖、上传不完整、代理缓存或被篡改；不关闭校验来恢复下载。
- 下载慢：检查服务器 4Mbps 共享带宽、剩余流量和并发，不能承诺国内一定秒下。
- 客户端仍访问 GitHub：核对实际安装版本和包内配置，按迁移流程处理。

## 旧版本历史记录（保留原记录，非当前状态）

以下内容来自以前的 Windows 与 GitHub 发布记录，本轮未重新验证其远端链接、签名或实机结果；其中“本机”“本轮”“Latest”“未提交”等均指当时，不是当前交付。

`0.2.0` 与 `0.2.1` 已包含上述差分下载缺陷，无法通过软件内更新跨过该版本。测试电脑必须手工安装一次 `0.2.2` 或更高版本；从该版本开始才能使用软件内更新。不得移动或覆盖既有标签来隐藏这一事实。

`0.2.5` 及更早的安装器允许在当前用户与所有用户之间选择，管理员会话执行自动更新时可能把安装范围迁移到 `C:\Program Files`。`0.2.6` 起安装器固定为当前用户模式，自动更新显式沿用当前可执行文件目录；普通安装和更新均不得静默改变安装范围或安装位置。

本机已使用正式私有 Release 完成 0.2.5 → 0.2.6 的检查、112,138,872 字节完整下载、退出安装与自动重启；更新后自定义安装目录和 HKCU `/currentuser` 安装范围均保持不变。

`0.2.7` 将软件更新窗口改为 Chromium 原生顶层模态，修复已加载工程节目单时更新窗口下半部分被工作区覆盖的问题。该版本已通过已加载工程的 Electron E2E、实际 Windows 打包产物视觉检查和 GitHub Windows 发布流水线；测试电脑可从 `0.2.6` 的更新中心直接检查并安装。

`0.2.8` 修复 Windows Web MIDI 输入只枚举但未显式打开的问题。进入预检或监听 P1 后，联动台会等待目标输入端口打开成功再订阅 MTC；取消订阅时关闭同一端口。同时修复 PowerShell 进程探测输出中文窗口标题时的编码乱码。该版本已通过 loopMIDI 系统回环、隔离 Electron 联动台运行回环和 [Release Windows #9](https://github.com/JinHe9527/tuanbo-yijianchufa/actions/runs/33098554787)；[v0.2.8](https://github.com/JinHe9527/tuanbo-yijianchufa/releases/tag/v0.2.8) 已发布为 Latest，测试电脑可从 `0.2.7` 的更新中心直接检查并安装。

`0.2.9` 修复集成中心首次进入时“一键识别并连接”读取旧 MIDI 枚举结果、错误清空已保存端口的问题；MIDI 初始化改为并发幂等，P1 直播放模式不再把可选控制输出误报为阻断。预检与演出控制统一按 500ms 有效窗口显示 MTC，未收到持续时间码时不再误报“稳定”或长期显示 `running`。软件更新窗口改为挂载到文档根节点的固定顶层遮罩，解决项目节目单覆盖更新窗口下半部的问题；遮罩覆盖整个视口，窗口保持 520px 最大宽度，并支持关闭按钮、外部点击和 Esc 关闭。[Release Windows #10](https://github.com/JinHe9527/tuanbo-yijianchufa/actions/runs/33102009894) 已全步骤成功，[v0.2.9](https://github.com/JinHe9527/tuanbo-yijianchufa/releases/tag/v0.2.9) 已发布为 Latest。

`0.2.10` 进一步把软件更新窗口收紧为真正的页面模态：窗口打开期间底层工作区不可点击、不可获得键盘焦点，关闭按钮自动聚焦，Esc 关闭后恢复交互。检查和下载更新产生的未知错误在进入界面前会移除当前 GitHub Token；素材缩略图生成失败也不再静默退化为通用占位，而是明确显示失败状态和根因。[Release Windows #11](https://github.com/JinHe9527/tuanbo-yijianchufa/actions/runs/33104369530) 已全步骤成功，[v0.2.10](https://github.com/JinHe9527/tuanbo-yijianchufa/releases/tag/v0.2.10) 已发布。

`0.2.11` 补齐软件更新取消路径：在系统确认框取消退出安装后，更新按钮会恢复可操作。同时加强未保存工程保护、工程和工作区布局恢复错误、MIDI 监听释放、媒体代理失败清理与最小窗口逐页边界检查。[Release Windows #12](https://github.com/JinHe9527/tuanbo-yijianchufa/actions/runs/33106205421) 已全步骤成功，[v0.2.11](https://github.com/JinHe9527/tuanbo-yijianchufa/releases/tag/v0.2.11) 已发布为 Latest。本机安装版回归已完成从本地同版本 0.2.10 构建到正式 0.2.11 的原目录升级、自动重启、最新版复查和零残留卸载。

`0.2.12` 修复工程恢复后演出控制早于桌面集成初始化完成、第一次点击预检可能无响应或误报的问题；演出控制会等待工程协调器和设备状态完成初始化。重复预检会复用相同端口与帧率的 MTC 订阅，不再人为断开正在输入的时间码。软件更新窗口改用 Chromium 原生 `dialog` 顶层模态并显式占满视口，修复特定窗口状态下遮罩只剩顶部一条、弹窗主体被工作区裁掉的问题。[Release Windows #13](https://github.com/JinHe9527/tuanbo-yijianchufa/actions/runs/33109764252) 已全步骤成功，[v0.2.12](https://github.com/JinHe9527/tuanbo-yijianchufa/releases/tag/v0.2.12) 已发布为 Latest。本机已完成 0.2.11 → 正式 0.2.12 的软件内更新与原目录自动重启验收。

`0.2.13` 收紧 P1 MTC 端口与启动链路：只有集成档案中精确配置、唯一且已连接的输入端口才显示就绪；端口断开、重新创建或同一档案改名后不会复用旧订阅。从集成中心顺序启动或在演出控制中人工重启 P1 时，联动台会先轮询等待目标端口出现，再建立 MTC 订阅，避免 P1 启动较慢时提前失败。“从头重新布防”会同时清除上一轮帧率和到达时间，防止短时间显示旧的绿色 MTC 状态。软件更新顶层模态增加跨全部工作区反复打开的渲染错误回归测试。Electron 从已结束支持的 37.3.1 精确升级至 39.8.10，正式运行依赖审计无已知漏洞。[Release Windows #14](https://github.com/JinHe9527/tuanbo-yijianchufa/actions/runs/33112754200) 已全步骤成功，[v0.2.13](https://github.com/JinHe9527/tuanbo-yijianchufa/releases/tag/v0.2.13) 已发布为 Latest；本机已完成 0.2.12 → 正式 0.2.13 的软件内更新、1920×1030 更新弹窗和零残留卸载验收。

`0.2.14` 本地候选版补齐参考音频提取、时间线素材时长与分层拖放/修剪、工作区交互及受管 OBS 输出清理，并把 P1 MTC 的“Windows 输入端口已就绪”和“P1 实际正在发送”明确分开。后续本地开发又补齐跨工程异步保存/导入隔离、跨盘素材路径防护、预检结果提交门槛、混合图片/视频的独立 OBS 输入、失败或超时后的保守活动来源跟踪、500ms 连续稳定判定、手动接管错过结算、外部程序所有权与重复启动保护。2026-08-31 已通过 37 个测试文件、237 项单元测试和 14/14 Electron E2E。实机确认 P1 1.14.2 播放时对 loopMIDI 与 Windows MIDI Services 软件环回均显示“未发送”且无 quarter-frame；界面和预检不再暗示仅选择虚拟端口即可完成现场签收。该版本仍是未提交、未发布的本地候选版；本轮按操作员要求不生成新安装包、不执行安装生命周期、不提交、不打标签、不推送、不发布，不能描述为正式 Release。

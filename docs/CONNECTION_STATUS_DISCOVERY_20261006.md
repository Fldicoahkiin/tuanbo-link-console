# 0.4.44 连接状态与 MA2 自动发现修复

## 已证实的代码问题

- OBS 自动连接把连接、配置刷新和场景清单放在同一个失败处理里。场景尺寸读取异常会把实际已连接的状态改成断开。
- 顶部视频还会采用旧的一键检查结果，覆盖当前连接状态。
- 顶部灯光在选择 MA2 网络编辑方式后，会改用 MA2 网络状态，忽略已配置的 MTC 接口，并跳转到错误设置位置。
- Windows 原生 MIDI 名单之前依赖设置页读取。最终安装包复测发现：重开后尚未进入设置页时，会误报端口未连接。本轮补充启动枚举，读取期间显示检测中。
- 本机开发版日志确认：一个失效的“显示器采集 3”尺寸解析抛错，导致整份场景目录失败，也会阻断播放前的 OBS 预检。改为仅记录该来源的尺寸异常，保留其他场景；网络请求本身的失败仍返回错误，不猜测尺寸。
- MA2 逐地址搜索把所有大于 /24 的网络裁成 /24。例如本机 10.39.12.89/22，以前不检查 10.39.13—15 的地址。此代码限制已复现，不等于已经确定测试主机漏检控台的唯一原因。

## 改动

- OBS 连接状态只由实际连接快照决定。清单失败单独显示、记录；一键连接仍继续检查预览。已断开的连接不会被迟到的清单请求恢复成已连接。
- 灯光固定显示选定 MTC 输出的状态，点击定位音频与 MIDI 的时间码设置。编辑灯光单独显示 MA2 工程通信。Windows 枚举可用为绿色“可用”，正在发送仍与控台实际出灯分开。
- 首次自动发现不要求先填写 IP：增加有限时间的 MA 网络端口组播监听，收集来源地址后通过只读 TCP 横幅验证 MA2 身份，唯一明确识别时沿用自动保存和连接流程。未知 UDP 来源、普通开放端口不能触发自动登录。
- 保留 ArtPoll、Windows 邻居目录和保存过的地址；按真实掩码检查 /20 及更小网络。更大网络不穷举百万地址，采用公告来源、邻居、保存地址与本地 /24。逐地址总量上限 8192，整个搜索最多 45 秒，支持取消。
- 只在主动搜索时监听 3 秒；每个 socket 最多 16 个组播成员，覆盖最多 8 个 IPv4 接口，结束后释放。不会加入控台会话、发送 Show 数据或修改控台设置。
- 搜索结果写入运行日志，包括网卡、掩码、覆盖范围、实际检查量、监听结果、耗时、取消和未完成范围。可从运行日志导出诊断包。

- `ma2-network-announcements.test.ts`：在本机实际 UDP 组播端口验证 256 个组的成员配置、收包和端口释放。使用测试端口与构造数据，不证明真实 MA2 报文兼容。
- `scripts/verify-obs-connection.mjs`：独立便携 OBS 32.2.2、无密码/有密码、真实连接与断开、创建测试专用的无效显示器来源，核对其他场景仍保留、该来源报错、顶部仍显示已连接。不修改用户 OBS 来源。

## 仍需现场验证

本轮不能宣称已在用户的 MA2 3.7.0.5 上完成自动识别。插线的物理连通、能观察网络来源、远程入口可达、登录成功、工程通信成功分别记录。控台不发送可观察公告、组播受限、IP 不可达或远程入口关闭时，自动搜索仍可能找不到可连接入口；不能把“未发现”写成“网络里没有控台”。多个已确认控台需要选定目标，不能擅自选择。

官方协议端口依据：[MA Network Switch 协议表](https://help2.malighting.com/Page/Network/factory_defaults/de/3.2)。组播范围研究线索：[MA 官方论坛的网络讨论](https://forum.malighting.com/forum/thread/51789-grand-ma-2-wireshark-packets/)；论坛信息不是本次实体实测证据。

本轮不替代 MA2 原生动作写回、真实灯具出光和六小时声光画面全链路验收。

## 本机画面与美颜诊断边界

本机重开加载修复后，从真实 OBS 32.2.2 读到 8 个场景，失效显示器作为单独警告返回。记录位于 `D:\Tuanbo-Current-Dev-044`。

诊断输入及时间戳位于 `D:\Tuanbo-Beauty-Live-Diagnostic-20261006`；重开后 `D:\Tuanbo-Beauty-Live-AfterRestart-20261006` 显示帧序号持续增加、画面年龄 0–16ms。本次证据不能确定旧画面停更的唯一触发条件，也不能当作用户所示人像已经恢复全部美颜效果的证明。此项保留后续实际人像复验，不能声明完整美颜验收通过。

## 0.4.45 搜索顺序回归修复

用户反馈相同现场环境中旧版能读、新版连地址都找不到。本轮比较旧实现（13f77eb）和 0.4.44，确认了一个新增的漏扫条件：扩大搜索网段后，仍逐网卡顺序扫描，而新增的 45 秒总期限和 8192 地址上限可能在轮到后面的控台网卡前用完。它是已复现的代码缺陷，但目前没有测试主机诊断，不能确定是现场唯一原因。

- 各网卡轮流分配探测机会，先覆盖原来会搜索的本地 /24，再扩展其余子网。8192 上限在轮流编排后应用，保存过的目标仍优先。
- 广播、MA 网络监听和邻居目录并行准备；不加大超时，不自动重试，不向候选设备发送登录或控制命令。
- 日志增加准备时间、端口检查时间及每个 /24 地址块的计划数、发起数、完成数、明确识别数。取消或达到期限时，未开始和未完成范围可以核对，不能把范围列表当成全部检查完毕。
- 回归覆盖 Wi-Fi /20 排在控台 /8 前，以及多个 /20 用完地址容量的情况。测试只验证搜索编排；本机 TCP 分段横幅验证仅代表测试服务器，不能算实体 MA2 兼容通过。

本轮没有改写控台 IP、Show 或用户工程。免激活测试渠道保持不变，安装包仍须从实际安装后的程序验收。现场实体 MA2 识别、登录和 Cue 读取仍待复验。

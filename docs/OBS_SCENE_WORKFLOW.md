# OBS 场景工作流

2026-09-13：机位使用 OBS 场景；低功率是可切换的显示偏好，不删除原有预览或工程内容。

- 每个机位对应 OBS 真实场景，保留已有显示、隐藏、拉腿、裁剪和滤镜。资源列表响应 OBS 场景变化。
- 拖入场景默认创建 5 秒片段，两端可拖动；宽度按实际时长绘制，与视频片段保持相同高度。
- 多层重叠时采用最上方可见轨道。机位结束后恢复下层仍有效的素材；素材位置为当前节目时间减片段开始时间再加素材入点。无下层内容时保持最后场景。音效片段没有画面，不遮挡下层，也不被上层机位或视频遮挡，片段期间一直出声；只剩音效时保持最后场景。没连 OBS 时编辑器预览按同一规则显示：机位上方的素材都画出来，机位垫在最下面。
- 机位临时覆盖期间，本应用素材在 OBS 内继续走媒体时钟但静音；切回前核对位置，不重新启动媒体。暂停节目会暂停全部活动媒体，继续时也恢复被机位遮挡的媒体计时，再恢复当前有效画面。准备已有的自有素材来源时，同样关闭激活重播、隐藏卸载和循环，避免旧来源切回后从头播放。
- 每个导入素材创建独立的应用自有 OBS 场景与来源。连接时导入会准备场景，也可点击“同步素材场景”；未连接时导入工程，预检时准备。仅管理自有来源，不删除用户已有场景和来源。
- 当前工程的素材场景从 OBS 列表拖入时，创建对应媒体片段，使用素材的时长、入点、暂停和定位控制；普通机位仍创建场景切换片段。
- 2026-11-09 用户要求“没有按照时间线触发是最严重的问题，一定不能再任何情况出现这种问题”：联动台播放时，画面动作（场景切换、素材开始和结束、继续播放）晚到也照样按顺序发出，不再因为晚了 100 ms 丢弃。晚 100 ms 以上写一条警告日志，晚 1 秒以上在播放器上标红。播放位置更新中断后按当前位置重建画面，中断期间的点 Cue 补发；跨过的持续段已结束的不再补发。
- 2026-11-09 根因排查（0.5.9）：OBS 卡住期间积压的画面动作，放开后合并成此刻应有的画面一次发出：被后面覆盖的机位切换不再一个个补发，积压期间开始又结束的素材不再启动，点 Cue 照常补发，晚了多少（从积压里最早该发的时间算）照样记日志、标红，只报一次。暂停时视频立刻跟着音乐暂停；正在发的那一步照常发完，还没发出的，继续时按当前位置补上；暂停那一刻正在开播的视频随后补一次暂停。已经发出的动作（成功或失败）不重发，暂停的时间不算晚到；暂停前停止失败的素材，继续时不再接着播。OBS 重连恢复画面时按了暂停，继续时先重新准备场景（被暂停打断的准备不算失败），再按继续的位置重建画面，素材先定位再统一播放；场景没重新准备好时机位照常恢复，标红写明素材可能播不出来。显示来源的隐藏只在确定没显示过时才省掉；停歌时隐藏还显示着的来源；从歌曲中间开始时，显示时长覆盖这个位置的来源照常显示、到时隐藏。预热好的素材晚到或在 OBS 里被改过位置时，按没预热的方式先切场景、再按音乐位置定位，场景照常切；同一素材预热失败只让这一段标红，后面的段照常预热，重新连上 OBS 后再准备一次。上一首停歌时画面清理失败只标红一次，下一首照常准备画面。OBS 请求的 2 秒从真正发出时算起：排队太久的只让这一条失败；发出后 2 秒没回应才判定 OBS 没响应、重新连接。一个画面动作含几个请求时不再整体按 2 秒算超时，等它真正结束再发下一个，晚回来的机位不会盖掉新机位。从歌曲中间开始时，一个机位或素材定位失败只标红这一个，画面照常准备。这次只改了画面动作；动作 MIDI 晚到仍按原来的规则（晚 100 ms 以上这一条不补发），要不要改等用户定（根因报告第 6 题）。
- 媒体控制回读实际状态和位置，指令接受不等于播放完成。定位误差超过 100 ms 时执行定位并确认；2 秒内未确认则显示目标与实际位置，不静默回到开头、不自动重发动作。
- 设置 → 画面与同步 → 低功率模式：开启时卸载软件视频/OBS 预览与动态频谱；关闭即恢复。该选项保存在本机，不修改时间线。正式视频解码、输出仍由 OBS 负责。
- OBS 画布在 OBS 中配置，内部主控和 P1 跟随分别选择。播放错误仅覆盖右侧频谱区域，X 或点击外部关闭。
- 不删除已有 Cue；保留工程 schema v1/v2 与 Command 撤销流程。推流、录像和直播伴侣开播不受控制。

## 时间线规则（2026-11-04）

规则只在 `packages/core/src/content-timeline.ts` 一处实现，编辑器的每个操作和正式播出都按它来。

- 素材片段（含音效）和机位都有长度，占一条轨道；同一条轨道上不重叠。其他 Cue（MIDI、OBS 动作等）是时间点，不占时间。
- 放下或拖到的位置在那条轨道上空着就放上去；被占了就在那条轨道正上方新建一条轨道放进去（同剪映）。“加到最上面”是顶层轨道空着就放顶层，否则新建最上层；拖到轨道下方的空白处新建最下层。
- 修剪碰到同轨相邻片段停住，视频和音效也不超出素材两端，至少一帧。切割素材时两段合起来正好用原来那段素材；机位也能切割。
- 没有内容的轨道自动去掉；锁定的轨道不能放入、移出、修剪或删除。
- 旧工程打开时整理一次（首次保存会留 .bak），逐帧画面和整理前一样：没有长度的机位补上它原来播出的长度（到任意轨道上下一个机位或画面开始，没有就到歌曲结束）；没分轨道的内容先放素材、再放机位；同一轨道上重叠的部分，后开始的移到它压住的部分正上方的新轨道。之后每次修改后同样整理，灯光修改不受影响。
- 没有任何画面时保持最后下画面的机位（按结束时间算，不是按开始时间）。
- 时间线、离线预览和正式播出用同一个判断（`SceneOutputTimeline`）：每段片段和机位哪些帧在播由 `airtime()` 给出，被上层机位挡住的部分在时间线上变暗，播放时只高亮正在播出的部分。修剪拖动时就按 `contentTrimBounds` 停在相邻片段和素材两端，和松手后的结果一致。编辑器的轨道（`ContentTracks`）和灯光工作台分开，灯光工作台不带这些编辑。
- 旧的「软件编排」（`obsOutputMode: 'managed'`，把素材放进“团播联动台输出”一个场景里叠）的代码已全部删除。工程文件里仍写 `obsOutputMode: 'scenes'`，让旧版本打开时也按场景播放；旧文件里的 `managed` 打开时改成 `scenes`。素材库只列 OBS 场景。旧工程里的“显示来源”Cue 照旧作用于当前播出场景（2026-10-19 的决定），不再往“团播联动台输出”里补层序动作。

## 定位与预览验证

- 设置“视频定位缓存”已接入素材同步和播放预检，默认关闭；开启后在工程 `cache/obs-seek-jpeg2000` 生成无损 JPEG 2000 视频、复制音轨的 Matroska 副本。原素材保持不变。生成前后验证原文件 SHA-256，复用时验证缓存 SHA-256；失败明确报告，不自动重发控制动作。关闭后下次同步或预检恢复原素材。
- 最终缓存采用 `-avoid_negative_ts disabled` 保持视频时间戳；FFmpeg 以绝对时间戳读取的 2.3、5.17、8.1 秒解码帧与原片 SHA-256 相同。当前 37.88 秒素材缓存约 179 MB。早期 H.264 缓存在 OBS 恢复播放后位置偏移约半秒，已弃用该格式。
- 本机 OBS 非零首次启动 2300 ms、向前定位 8100 ms、向后定位 5170 ms 均通过实际位置核对，耗时分别 132、88、88 ms，证据为 `acceptance-20260913-obs-seek/probe-result.json`。启用缓存的整条节目实测 0 ms 首播和 8100 ms 机位恢复成功。测试后关闭缓存选项并恢复原素材。首次格式切换曾出现状态确认超时，之后的独立验证通过，尚需覆盖冷启动及更多素材类型。
- 普通模式预览已接入场景播放所用的时间线选择结果：机位时读取完整 OBS 场景，素材时只预览被选中的媒体；机位期间不挂载下层视频。完整场景只读显示，使用 OBS 画布尺寸。Electron 已验证场景图片出现、无变换手柄、低功率卸载与恢复；本机已确认“场景 2”返回 540×960 预览、画布为 2160×3840。任意定位仍单独待验收。

当前检查：629 单测通过、32 跳过；类型检查、Lint、独立构建通过；两项 Electron 测试覆盖错误关闭、场景拖动、场景预览、素材场景拖入、低功率切换和定位缓存设置。实测不支持“绝对 0 延迟”的承诺，已请求用户确认以实际位置和耗时作为验收标准，目标尚未标记完成。

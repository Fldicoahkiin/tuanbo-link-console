# OBS 场景工作流

2026-09-13：机位使用 OBS 场景；低功率是可切换的显示偏好，不删除原有预览或工程内容。

- 每个机位对应 OBS 真实场景，保留已有显示、隐藏、拉腿、裁剪和滤镜。资源列表响应 OBS 场景变化。
- 拖入场景默认创建 5 秒片段，两端可拖动；宽度按实际时长绘制，与视频片段保持相同高度。
- 多层重叠时采用最上方可见轨道。机位结束后恢复下层仍有效的素材；素材位置为当前节目时间减片段开始时间再加素材入点。无下层内容时保持最后场景。音效片段没有画面，不遮挡下层，也不被上层机位或视频遮挡，片段期间一直出声；只剩音效时保持最后场景。没连 OBS 时编辑器预览按同一规则显示：机位上方的素材都画出来，机位垫在最下面。
- 机位临时覆盖期间，本应用素材在 OBS 内继续走媒体时钟但静音；切回前核对位置，不重新启动媒体。暂停节目会暂停全部活动媒体，继续时也恢复被机位遮挡的媒体计时，再恢复当前有效画面。准备已有的自有素材来源时，同样关闭激活重播、隐藏卸载和循环，避免旧来源切回后从头播放。
- 每个导入素材创建独立的应用自有 OBS 场景与来源。连接时导入会准备场景，也可点击“同步素材场景”；未连接时导入工程，预检时准备。仅管理自有来源，不删除用户已有场景和来源。
- 当前工程的素材场景从 OBS 列表拖入时，创建对应媒体片段，使用素材的时长、入点、暂停和定位控制；普通机位仍创建场景切换片段。

- 2026-11-09 根因排查（0.5.9）：OBS 卡住期间积压的画面动作，放开后合并成此刻应有的画面一次发出：被后面覆盖的机位切换不再一个个补发，积压期间开始又结束的素材不再启动，点 Cue 照常补发，晚了多少（从积压里最早该发的时间算）照样记日志、标红，只报一次。暂停时视频立刻跟着音乐暂停；正在发的那一步照常发完，还没发出的，继续时按当前位置补上；暂停那一刻正在开播的视频随后补一次暂停。已经发出的动作（成功或失败）不重发，暂停的时间不算晚到；暂停前停止失败的素材，继续时不再接着播。OBS 重连恢复画面时按了暂停，继续时先重新准备场景（被暂停打断的准备不算失败），再按继续的位置重建画面，素材先定位再统一播放；场景没重新准备好时机位照常恢复，标红写明素材可能播不出来。显示来源的隐藏只在确定没显示过时才省掉；停歌时隐藏还显示着的来源；从歌曲中间开始时，显示时长覆盖这个位置的来源照常显示、到时隐藏。预热好的素材晚到或在 OBS 里被改过位置时，按没预热的方式先切场景、再按音乐位置定位，场景照常切；同一素材预热失败只让这一段标红，后面的段照常预热，重新连上 OBS 后再准备一次。上一首停歌时画面清理失败只标红一次，下一首照常准备画面。OBS 请求的 2 秒从真正发出时算起：排队太久的只让这一条失败；发出后 2 秒没回应才判定 OBS 没响应、重新连接。一个画面动作含几个请求时不再整体按 2 秒算超时，等它真正结束再发下一个，晚回来的机位不会盖掉新机位。从歌曲中间开始时，一个机位或素材定位失败只标红这一个，画面照常准备。这次只改了画面动作；动作 MIDI 晚到仍按原来的规则（晚 100 ms 以上这一条不补发），要不要改等用户定（根因报告第 6 题）。自动化验证通过，未实机验证。
- 2026-11-09（0.5.9）画面清理、拖动定位和下一首的提前准备：停歌时画面没有清理干净，只在画面那边清理的地方记一次运行日志，日志保留 OBS 的原话、请求名和来源名，界面显示看得懂的原因；不自动重试清理。歌还在台上（准备中、播放中、暂停）就在这首歌上标红、照常播；已经停下的（按停止，或最后一首播完）在播放器上马上提示一次；自动换到下一首的，在下一首上标红一次；关闭节目时交还给画面那边，关闭节目不会因此失败：之后打开的节目已经有歌在台上，就标在这首歌上（排在它原有的红字前面），否则由之后开播的第一首歌标红一次；下一个节目是 P1 跟随时只记运行日志，界面上不标红（已知限制）。提示过以后，之后的停止、选歌和下一首都不再重复。这首歌开播时的其他红字（画面那边的、画面准备失败、停止时关灯没准备好、时间码没发出、动作 MIDI 断开）和“上一首（上一次）的画面没有清理干净”一起显示，时间码或动作 MIDI 接口回来后只清掉自己那条；播放中出现的新故障照常替换它们，下一次播放或定位重新开始。这首歌自己的画面一秒内没准备好被取消、取消时又没清理干净，写“取消的画面准备没有清理干净，不影响播放”。画面清理失败的原因只说出了什么事，不带画面准备失败才用的“请重新同步素材后再播放”。拖动定位还没完成（定位指令或新位置的画面还在准备）时按播放或暂停，以最后按的那一下为准：定位完成后停在新位置，或从新位置接着播，用的就是这次定位准备好的画面，这首歌后面的画面照常按时间线切换；重复按只接着播一次。是不是在曲尾按拖到的位置判断：歌停在曲尾、拖回前面再按继续，从拖到的位置接着播。歌在准备时 MIDI 播放键（note 1）不起作用，和播放按钮、空格一致。下一首的提前准备被这首歌停下或播完打断算取消，不记失败，也不记成“素材没有准备好”；上一首停了、下一首还没接手时提前准备真的失败了，照样记一次日志，下一首照常重新准备画面。重新连上 OBS 后恢复画面途中停歌、暂停或换歌，恢复按取消结束，不算素材没有准备好。未实机验证。

## 时间线规则（2026-11-04）

规则只在 `packages/core/src/content-timeline.ts` 一处实现，编辑器的每个操作和正式播出都按它来。

- 素材片段（含音效）和机位都有长度，占一条轨道；同一条轨道上不重叠。其他 Cue（MIDI、OBS 动作等）是时间点，不占时间。
- 放下或拖到的位置在那条轨道上空着就放上去；被占了就在那条轨道正上方新建一条轨道放进去（同剪映）。“加到最上面”是顶层轨道空着就放顶层，否则新建最上层；拖到轨道下方的空白处新建最下层。
- 修剪碰到同轨相邻片段停住，视频和音效也不超出素材两端，至少一帧。切割素材时两段合起来正好用原来那段素材；机位也能切割。
- 没有内容的轨道自动去掉；锁定的轨道不能放入、移出、修剪或删除。
- 旧工程打开时整理一次（首次保存会留 .bak），逐帧画面和整理前一样：没有长度的机位补上它原来播出的长度（到任意轨道上下一个机位或画面开始，没有就到歌曲结束）；没分轨道的内容先放素材、再放机位；同一轨道上重叠的部分，后开始的移到它压住的部分正上方的新轨道。之后每次修改后同样整理，灯光修改不受影响。
- 没有任何画面时保持最后下画面的机位（按结束时间算，不是按开始时间）。
- 时间线、离线预览和正式播出用同一个判断（`SceneOutputTimeline`）：每段片段和机位哪些帧在播由 `airtime()` 给出，被上层机位挡住的部分在时间线上变暗，播放时只高亮正在播出的部分。修剪拖动时就按 `contentTrimBounds` 停在相邻片段和素材两端，和松手后的结果一致。编辑器的轨道（`ContentTracks`）和灯光工作台分开，灯光工作台不带这些编辑。
- 播放中改画面（2026-11-09，0.5.9；2026-11-12 起这一遍就用上，见上文 R9 那条，本条只剩编辑器怎么标）：联动台播放拿着一首歌（准备中、播放中、暂停）时，改过、还没送到 OBS 的素材和机位画成虚线框，写“正在送到 OBS”，不标正在播出；删掉的不再画出来，在时间线上方的提示里计数，并写明它们照常播出。只算 OBS 真会播的部分：停用的 Cue、隐藏轨道上的素材、只发 MIDI 的 Cue 不算，“显示来源”Cue 算。正在播出的高亮按画面在播的那一版算（开始那一版，或画面已经用上的新一版），变暗和离线预览按编辑器里的时间线。整段播放期间时间线上方一直留着这一行提示，按住鼠标拖动或修剪、从素材库往时间线拖素材时，它都不出现也不消失，轨道不会在编辑中途上下跳；松手或放下素材时，先按松手那一刻看到的轨道放下，这一行之后才跟着出现或消失。界面重新加载后接回的节目和这里打开的工程不是同一版时，提示写“无法确认 OBS 按哪一版时间线在播”和原因，不标任何正在播出或改过的部分。后台的节目还没回复它在播哪一版之前，也写“无法确认 OBS 按哪一版时间线在播”，原因写“正在确认联动台播放在播哪一版”，说明确认以后会自动更新，不叫操作员停歌，也不标正在播出；回复以后按回复显示。主进程接回节目后先回复，再记日志，日志写不进去也不耽误回复。接回的是不是同一版只在 `program-attachment.ts` 判断。停止后标记和提示都去掉，再播就按编辑器里的时间线。这些判断只在 `view-models/picture-on-air.ts` 和 `view-models/pending-picture-edits.ts`，编辑器的走带用同一个“联动台播放拿着哪首歌”。播放中改的画面 2026-11-12 起这一遍就用上（R9）。未实机验证。

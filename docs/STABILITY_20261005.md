## 2026-10-06 设备观察年龄与后台画面截止时间

### 原生音频/MIDI 可行性引擎（尚未接管正式播放）

`tools/playback-engine/` 包含 Windows C 引擎、独立 WinMM 接收探针和固定编译器构建脚本。

- WASAPI 共享模式实际输出；按设备位置 / `IAudioClock::GetFrequency` 换算播放位置，保留关联的 QPC 时间。
- 磁盘线程分块读取，固定 262144 帧立体声 PCM 缓冲约 1MB；控制、音频、MIDI、诊断分线程。
- MIDI 在原生线程发送，读取同一设备播放时钟；不依赖 React、页面帧率或 JavaScript 定时器。
- 保护旧代数命令、暂停/定位/停止的发送边界；格式与范围由 TS Zod 和原生端分别校验。
- 音频欠载同时检查磁盘缓冲和 WASAPI 中途空缓冲；时钟过期和 MIDI 发送异常有独立错误状态。它们发生时属于验收失败，不能计为正常稳定运行。
- 控制进程通过有界请求队列和版本化 DTO 访问。每条响应限制容量，主进程繁忙后合法的批量响应不会被错误判为超限。
- 引擎窗口提供 PID 对应的唯一实例名称，供 OBS 精确选择。实测发现 `WS_EX_TOOLWINDOW` 被 OBS 排除，已改为隐藏所有者持有的非激活窗口。
- FFmpeg PCM 准备服务校验原文件及缓存指纹，整段解码不自行叠加 P1 起点/裁剪；数量、字节预算和播放租约控制淘汰。取消任务不发布残缺缓存，不强杀解码进程。

**当前限制**：已接主进程 IPC 和发布资源清单，尚未接管正式播放按钮或验证最终安装包；24/25/30fps；29.97df、淡入淡出、完整服务故障恢复、跨进程缓存所有权、后台 OBS/灯光调度及统一播放快照仍待实现/验证。端点选择本机验证见上方10月6日记录。现有正式播放器保持原路径。不能把此原型称为完整的新播放引擎交付。

依据：[Microsoft IAudioClock::GetPosition](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclock-getposition)；[OBS 官方窗口筛选实现](https://github.com/obsproject/obs-studio/blob/master/libobs/util/windows/window-helpers.c)。官方资料用于解释 API 和筛选规则，实际接入结果以下方本机测试为准。

### OBS 请求派发与连接隔离

旧适配器把已经开始执行的网络 Promise 交给超时包装，因此包装层无法限制实际发出的数量；目录读取还会同时展开全部来源。现在请求改为延迟函数，由 `ObsRequestScheduler` 派发：

- 总计最多四个在途请求，背景查询最多三个，预览最多一个；最多 128 个待发请求。目录遍历也采用有界工作循环，2000 来源不会一次挤满队列。
- 待发动作按停止/暂停、控制、背景查询、预览排序。已发送请求不能被协议撤回；没有宣称可抢占在途 OBS 写入。
- 原 2 秒截止时间包含排队时间；未发出与执行结果不明分别报错。已发送请求超时后停止此连接的后续派发并标记错误，不自动重发。
- 连接代数贯穿动作、素材准备、画布编辑及目录/预览操作。断线与明确重连作废旧操作，旧操作即使等待后恢复也不能借新连接继续发出。
- `obs-request-scheduler.test.ts` 和适配器回归覆盖预览占用、控制保留通路、优先停止、超时、容量、迟到结果和跨连接旧操作。`artifacts/native-audio-obs-o3OeWD/report.json` 验证真实隔离 OBS 同时进行目录读取、预览和通过正式适配器切场景，切场景后测试音仍被采集。

补齐素材准备、来源编辑的连接上下文后再次验证：`artifacts/native-audio-obs-keoSTR/report.json`，真实 OBS 目录、预览、场景确认和采集电平均通过。所有隔离 OBS 测试实例均已正常关闭，用户原有 OBS 未关闭。

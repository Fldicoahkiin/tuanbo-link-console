# 单主机授权实施记录

## 2026-11-09 停止不过授权，演出的授权跟后台节目走（长期规则）

0.5.9 现场问题后定下的长期规则。规则测试是 [license-rules.test.ts](../apps/desktop/src/main/link/license-rules.test.ts)，在授权到期、离线使用期到、系统时间被调回三种情况下各跑一遍。改代码让它失败就是违反了这条规则，不能靠改测试过关。

1. **停止、关灯、暂停、静音、隐藏一律不过授权。** 它们只是结束授权检查通过后开始的东西，授权失效时也要照常生效：
   - MA2：执行器或序列的 Off（`link:ma2-play-cue` 里 action 为 off）、取消灯光会话、停止试听。
   - 播放：停止、暂停、停发时间码。
   - OBS：媒体停止和暂停、静音、隐藏、停止节目画面、取消预载、自有素材的结束阶段。
   - 动作 MIDI：Note Off 和 MSC Stop。
   - 界面结束这一场运行、关美颜。
2. **开始输出和发新内容仍要授权**：MA2 的 Go 和 Goto、试听播放、开播、准备下一首、OBS 准备画面和开始媒体、打开后台节目，以及其余 MIDI（Note On，包括力度为 0 的 Note On，CC、PC、MSC Go 等）。
3. **正在进行的演出跟后台节目走，不跟界面走。** 界面确认这一场运行时，后台节目如果正在准备、播放或暂停，节目就和界面一起持有授权：界面重新加载、短暂空闲都不打断这场演出。节目一停（停止、出错、关闭、被替换）就放手。节目自己拿不到授权。演出停下、界面这一场也结束后，新开一首要重新检查授权。

在代码里的落点，每件事只有一处：

| 事情 | 地方 |
| --- | --- |
| 哪些请求不过授权 | `apps/desktop/src/main/link/license-access.ts` 的 `needsProductLicense`，界面的 IPC 和后台节目都经它判断 |
| 哪些 MIDI 不过授权 | `packages/core/src/midi-program.ts` 的 `midiMessageNeedsLicense`，按发出去的字节判断；界面的 MIDI 适配器（`link-midi-adapter.ts`）和后台节目（`native-midi-ports.ts`）都用它，两边一致由 [midi-license-rule.test.ts](../apps/desktop/src/renderer/src/registry/midi-license-rule.test.ts) 守着 |
| 后台节目的关灯请求和运行状态怎么接到授权检查 | `apps/desktop/src/main/link/program-license.ts`，link-main 只调用它 |
| 授权由谁持有 | `LicenseAccess`：界面一份，后台节目一份 |

没有保证的地方：停止后马上开下一首，如果下一首的准备比界面的“空闲”先到主进程，这一首仍按界面这一场的授权通过。0.5.9 之前只有一份会话授权时也是这样，这次没有改。

停止后马上关闭后台节目（改了片段、重建播放器、关窗口）时，停止欠下的执行器 Off 在关闭时补发一次，不重试。补发失败时节目已经关了，播放器上不再显示，所以失败按错误写进运行日志，窗口还开着时用红色提示告诉操作员去控台上关掉这首歌的执行器（`main-process-errors.ts` 的 `closedProgramFaultReporter`）。没有窗口看得到播放器时（节目已关闭，或界面退出、重新加载后节目在后台接着播），补发的 Off 失败也是当场按错误写进运行日志，并在窗口里标红一次；界面正在重新加载时，等新页面打开节目时再显示。红字写这次 Off 所属的那首歌（不是正在放的歌），先说结果、再说原因、最后说怎么办，不重发；窗口开着时播放器里的提示也是这一句，日志记在那首歌上。

界面重新加载（错误画面上的“重新进入工作区”）和界面进程意外退出走同一处处理（link-main 的 `releaseGonePage`；`window-page.ts` 跟着窗口里的页面）：新页面换上之后，才放开上一页占着的 MIDI 接口、主进程在等它回答的保存和节目。正在准备、播放或暂停的节目留在后台接着放，打开同一个工程就接回，不停歌，也不重新检查授权（上面第 3 条）；没在放的就关掉。只放行页面自己发起的同一网址重新加载，别的跳转（链接、拖进窗口的文件）一律拦下，也不放开任何东西。

状态：已实现，自动化验证通过（单测、类型检查、lint），**未实机验证**。要在现场 Windows 和实体 MA2 上确认：

- 授权到期、离线使用期到、系统时间被调回时按停止，控台上这首歌的执行器关掉。
- 停止后马上改片段，这首歌的执行器照样关掉。
- 界面重新加载后接回正在播放的节目，演出不中断。设置里选的不是默认声卡时也一样：界面第一次打开就用设置里的声卡，不再先用默认声卡开一次、再重开把接回的节目关掉（2026-11-09，`program-attachment.ts` 的 `followAudioConfiguration`）。
- 关闭时补发的 Off 发不出去（例如控台断网）时，窗口里出现红色提示，运行日志里有一条错误。
- 错误画面上点“重新进入工作区”：界面重新加载，正在放的歌不断，打开同一个工程能接回控制；往窗口里拖文件，界面用的 MIDI 接口照常能用。

## 本轮已实现

- 设置 → 外观与更新 → 本机授权：显示机器码、当前状态、客户、使用期限及升级期限；导出申请、导入授权文件、刷新状态。运行中禁止更换许可。
- Windows MachineGuid 经产品域隔离 SHA-256 后作为本轮机器码，不向发行方导出原始标识。不是设备私钥方案；克隆 Windows、重装 Windows 的处理仍需完善。
- 主进程验证 Compact JWS / Ed25519；校验可信 keyId、签名、产品、主机、授权类型和期限。renderer 不拥有签名能力。
- 买断使用期限为空，升级服务到期不影响本轮有效性判断；订阅和试用按 useUntil 到期。无效、跨机器和已到期许可不覆盖现有有效文件。原子保存，不写进工程。
- 独立发行方工具 scripts/license-issuer.mjs：生成 Ed25519 密钥，针对机器码签发许可；拒绝覆盖已有文件。没有将生产私钥放入仓库或客户端。

## 发行方离线操作

1. 客户在本机授权页导出申请 JSON；其中只有产品、协议版本和机器码。
2. 发行方保管私钥，并将对应公钥 JSON 内容配置到 src/main/link/license-public-keys.json 后构建客户端。只能分发公钥，私钥应放仓库之外并做受控备份。更换公钥需保留历史公钥以兼容已售许可。
3. 核对订单与销售规则后签发：

```powershell
node scripts/license-issuer.mjs keygen --kid release-1 --private D:/LicenseVault/signing.pem --public D:/LicenseVault/public.json
node scripts/license-issuer.mjs issue --kid release-1 --private D:/LicenseVault/signing.pem --public D:/LicenseVault/public.json --request D:/LicenseVault/request.json --customer "客户公司" --kind perpetual --updates-until 2027-09-21T00:00:00Z --out D:/LicenseVault/customer.tbllicense
```

上面为操作示例，未执行生产签发。路径父目录需预先存在，日期按真实订单填写；订阅和试用还需 --use-until ISO 日期。所有参数中的时间均明确为 UTC，桌面按本地时间展示。

4. 客户导入 .tbllicense；不同机器会明确拒绝。记录订单号、licenseId、机器码、授权类型和期限。离线手工发货不自动收款、不自动退款。

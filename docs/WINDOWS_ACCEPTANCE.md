## 正式播放器长时间运行（2026-10-24）

构建 `1401629`（master，含 9b3daa3）。开发机 DESKTOP-2C8JIC2，真实 OBS，原生播放引擎（WASAPI 默认输出，48 kHz）。时间码发到 loopMIDI 测试口 `TBLINK SOAK MTC`，同一口的输入端用 WinMM 接收并逐帧解码；onPC 不参与。工程是验收工程的副本，三首歌循环（1 灯光 + 机位 + 387 画面 / 2 透明叠加 + 显示来源 / 3 纯音频），曲尾接下一首，音量 10%。同一应用实例连续运行 288 分钟，累计播放 180 分钟：每段持 GUI 锁连播 30 分钟，段间停播、断开 OBS、最小化并释放锁 10 分钟（其他会话占锁时等待，共约 38 分钟）。

- 日志噪声：每次换歌都记一条 warning「播放按钮不可用：正在准备音频」（537 条）；歌 2 每播一次记一条「素材清晰度」warning（106 条）。两者都不是故障，建议准备中改记 info、清晰度提示每个工程只记一次。
- 歌 1 的灯光状态为「需处理」（控台 Timecode 9907 的时间依据需要重新核对），每次开播都按开播前检查走无灯光播放并记两条 warning（113 次），本轮不发时间码，符合设计。
- 每段最后一首被测试脚本在约 7 秒处停止，因此只出现两次场景切换，不计为异常。

未覆盖：onPC 或实体 MA2 跟随时间码；真实 USB MIDI 接口断电重连（列入用户现场测试）；单段 30 分钟以上不间断播放。

### 时间码与动作 MIDI 端口拔插（2026-10-24）

同一构建 `1401629`。用 Windows MIDI Services 的 `midi.exe loopback create/remove` 建删一对临时回环口模拟拔插（应用发到「TBLINK REPLUG A」，接收端用 WinMM 读「TBLINK REPLUG B」，端口消失后自动重开）；loopMIDI 和已有端口都没动。歌 2 带时间码，并在第 1、3、5… 秒各发一条 Program Change。结论只看接收端收到的数据。

| 情况 | 本首剩余部分 | 恢复操作与结果 |
|---|---|---|
| 播放中拔插 | 时间码标红「Windows MIDI 输出失败（错误码 6）」，动作 MIDI 同样报错停发，音频继续 | 停止后重播：275 ms 内恢复连续的四分之一帧，PC 1/3/5 送达，时间码与播放位置偏差 13–20 ms |
| 暂停中拔插 | 继续播放后时间码标红（错误码 6），动作 MIDI 照常送达（PC 7/9/11） | 停止后重播：287 ms 内恢复，偏差 12–17 ms |
| 两首之间拔插 | — | 播放下一首：在端口本身可用的 3 轮里，259–324 ms 内恢复，PC 1/3/5 送达，偏差 17–22 ms |

两首之间拔插另有 6 轮接收端什么都没收到，应用也没有报错。最后一组 4 轮在播放期间由另一个新进程往同一端口发对照消息：应用恢复的 2 轮，对照消息都送达；应用没送达的 2 轮，对照消息同样没有送达。由此判断这几轮是这对临时回环口重建后不再送达（测试环境），不是应用不发；前 4 轮失败没有对照，按同一现象归类。[下一节](#port-auto-recovery-20261024)进一步缩小了范围。需要注意：WinMM 只报告「已交给驱动」，不报告是否送达，端口处在这种状态时任何发送方都无法察觉。真实 USB MIDI 接口断电重连列入用户现场测试。

### 端口回来后自动恢复（2026-10-24，构建 825c584，未发布）

时间码与动作 MIDI 在同一端口回来后自动重开（授权见 AGENTS.md）。回环口改用固定的 `--unique-identifier` 重建：重建约 0.6 秒，回来的是同一个设备，接近把接口插回同一个 USB 口。接收端用 WinMM 读 B 端，能解 SysEx。歌 2 在每个奇数秒发一个动作，依次为 Note On、CC、Program Change、MSC Go，数值等于所在秒，收到的每个动作都能对回时间轴。时间码与动作走同一口（A→B），以及分走两口（A→B、C→D，两口同时拔插）各测一遍。

设备上验证过：

| 项目 | 结果 |
|---|---|
| 基线（两种接法） | Note/CC/PC/MSC 全部送达，相对歌曲位置 −6～+3 ms；时间码连续，无跳变、无乱序 |
| 播放中拔插 | 音频全程不停。端口回来后，应用第一次重开时 Windows 还没建好（发送报错码 1），下一秒重开成功。时间码 4.3–7.4 秒后恢复，日志记录中断起止时间；动作 MIDI 4.2–4.3 秒后恢复，日志写明「中断期间跳过 3 个动作，未补发」并带起止时间；恢复后发送计数持续增长（每秒约 120 个四分之一帧） |
| 暂停中拔插 | 继续播放时时间码 0.2–1.2 秒恢复；动作 MIDI 在继续播放时照常重新准备 |
| 两首之间拔插 | 下一首照常准备，引擎持续发送 |

未验证（接收端）：应用运行期间只要回环口重建过，接收端就收不到任何数据，独立进程发出的对照消息同样收不到。没有应用运行时，同样的删除、重建、跨进程收发每次都送达（4/4 轮；另一个进程在删除前后一直占着输出或输入、带 SysEx 缓冲区、或一直发到报错码 6，也都送达，6/6 轮）。Windows MIDI Services 的会话快照显示：每重建一次，electron.exe（界面的 Web MIDI）和播放引擎在同一端点上的连接数都会多一个，旧连接不释放（A 端从 x2 增到 x5，引擎从 x1 增到 x7）；新启动的进程只有 1 个连接。因此「恢复后接收端以收到为准」尚未通过，待以下两项：同一进程在端口删除前已连接、重建后再连接时是否会让整个端口不再送达（开发机空闲后复现）；真实 USB MIDI 接口插回同一 USB 口（用户现场）。

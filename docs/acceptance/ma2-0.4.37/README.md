# MA2 时间码模式下序列池 Cue 不再阻断音乐 · 0.4.37

## 根因

`compileLightingPackets` 在时间码输出模式发现任何本地序列池 Cue（无执行器号）就抛错。调用发生在内部音频 `audio.play()` 前，因此已有控台原生 Timecode 和实际音频均未启动。该判定错误地把“本地不能通过执行器时间码单独发出序列池 Cue”上升成“整首歌不能播放”。

## 改动

时间码模式不为本地 Cue 生成 MIDI 或网络指令，不自动改变输出方式；只要没有其他独立的准备失败，歌曲和启用的时间码继续按现有偏移播放。播放主控给出非阻断提示，说明本地序列池 Cue 没有单独发送，应确认其已编排在控台原生时间线。直接 MIDI 模式的无执行器 Cue 仍拒绝伪造执行器；网络模式继续要求明确连接控台。未改变原生 XML、配对和写回保护。

## 验证

`verify.log`：完整类型、单元测试、lint、构建和桌面产物校验通过。针对含原生绑定及本地池 Cue 的测试，验证音频启动、480秒原偏移 MTC、暂停/继续、断开的 MA2 网络不会被自动调用。`packaged-e2e.log`：最终打包程序的歌曲播放与时间码调度、混合动作缓存重启两条流程通过；模拟序列池 Cue 下音频继续，时间码输出持续。未用这些测试声称现场灯具已出光。

## 2026-09-28 无网线声光同步复核

明确区分电脑到控台的 MA2 局域网（仅读取、编辑同步、网络 Cue 调用）和 MIDI 时间码演出链路。内部主控从实际音频位置加上原歌曲起始偏移输出 MTC；不要求联动台与控台建立 MA2 网络会话。`mtc-scheduling.spec.ts` 的打包版验收现在使用：MA2 网络为 disconnected、网络 Cue IPC 一旦被调用立即报错、保存的控台原生 Timecode 2、非零 480000ms 歌曲偏移、模拟 USB-MIDI 输出。检查第一个全帧 MTC 为 00:08:00:00（30fps）、MTC 后续消息持续、网络 Cue 调用 0 次、音频继续播放、暂停仍停止输出。结果见 `offline-mtc-packaged-e2e.log`。这是软件和 MIDI 数据层验证，不是现场控台接收或灯具出光证明。

现场必须有非网线的实际时间码通路：电脑可见的 MIDI 输出经 USB-MIDI 接口连接控台 MIDI In（或已有的等价 MTC 链路）。控台的 MIDI TC 输入应映射到原 Timecode Show 使用的 Slot；当前截图显示 Show 的 TC Slot 2，但不能仅凭截图保证控台当前路由和 AutoStart/Play 状态。MA2 官方文档说明外部 MTC 可驱动 Timecode Show，MIDI In 默认路由 Slot 2，路由可在控台配置，外部 Show 需进入 Play 等待或启用 AutoStart。无物理 MIDI/LTC 输入或控台 Show 未处于播放状态时，电脑软件不能凭空让控台出灯。单独点击素材库 Cue 属于另一条直控功能；若无网络，它需要已知执行器地址和控台已配置的 MSC MIDI 输入，不等同于整首歌的 MTC 跟随。
